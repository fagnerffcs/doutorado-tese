\section{Infrastructure as Code}
\label{sec:iac}

As cloud computing introduced the capability to provision resources via APIs, the traditional manual approach to system administration became a critical bottleneck. Infrastructure as Code (IaC) emerged as the solution to this scalability challenge. Defined by \citeonline{morris_2016}, IaC is the practice of managing and provisioning computing infrastructure through machine-readable definition files, rather than through manual hardware configuration or interactive tools.

Fundamentally, IaC applies software engineering principles such as version control, automated testing, and Continuous Integration (CI) to infrastructure operations. This paradigm shift ensures that the environment is idempotent, meaning that applying the same configuration multiple times always converges to the exact same system state, eliminating the ``configuration drift'' common in manually managed servers.

\subsection{Immutable Infrastructure and Scientific Reproducibility}
\label{subsec:pets-vs-cattle}

The necessity for IaC in modern architectures is conceptually summarized by the ``Pets vs.\ Cattle'' metaphor \cite{bias_2016}. In traditional IT (pre-cloud), servers were treated as ``Pets''---unique, hand-crafted systems requiring manual maintenance. Conversely, cloud-native environments treat infrastructure as ``Cattle''---standardized, disposable, and automatically replaceable instances built from declarative specifications.

Within the context of this doctoral research, adopting an immutable infrastructure paradigm is a strict methodological requirement (\texttt{ConH1} and \texttt{ConH2}). To answer the research questions regarding the diagnostic effectiveness and resource overhead of the proposed observability architecture (PANOPTES), the experimental environment must be completely deterministic and reproducible. Relying on manually configured servers would introduce configuration drift and observational bias into the Mean Time to Diagnose ($MTTDiag$) and Diagnostic Accuracy ($Acc$) measurements.

Therefore, IaC is employed across three distinct layers to guarantee structural parity between the Vanilla control baseline and the PANOPTES experimental group:

\begin{itemize}
    \item \textbf{Virtualization and Node Provisioning Layer (K3d / Multipass):} Employed to instantiate the 3-node Infrastructure as a Service (IaaS) topology ($1\text{ Control Plane} + 2\text{ Workers}$). As formalized in \textbf{ADR-0006} (Section~\ref{subsec:virtualization-evolution}), the provisioning scripts deterministically launch the multi-node cluster with identical per-node hardware allocations ($2\,\text{vCPUs}$ and $4096\,\text{MiB}$ RAM enforced via Linux \texttt{cgroup} quotas on WSL2 in K3d or Hyper-V VMs in Multipass), eliminating Type-2 hypervisor I/O bottlenecks.
    \item \textbf{Configuration Layer (Ansible):} Responsible for configuring the cluster baseline, kernel parameters, namespaces, and workload scaling rules (\textbf{ADR-0005}). Ansible ensures that the Vanilla and PANOPTES environments share identical runtime configurations and network routing rules.
    \item \textbf{Application and Telemetry Layer (Helm):} Used to package and deploy the reference architecture and fault injection operators. Both the PANOPTES observability stack (OpenTelemetry Collector, Prometheus, Loki, Tempo, and Grafana) and Chaos Mesh are instantiated deterministically via version-locked Helm Charts.
\end{itemize}

This multi-layered declarative approach ensures that the reference architecture remains a verifiable artifact that can be audited, versioned, and replicated by the scientific community, fulfilling the rigor requirements of the Design Science Research (DSR) framework.
