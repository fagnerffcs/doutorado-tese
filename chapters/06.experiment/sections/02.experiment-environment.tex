\section{Experimental Environment}
\label{sec:experimental-environment}

The experiments were conducted in a controlled laboratory environment designed to simulate a private cloud infrastructure while guaranteeing strict hardware parity across all evaluated scenarios. While enterprise production environments typically require a High Availability (HA) control plane with at least three master nodes \cite{brendan_tracey_2018} to ensure \texttt{etcd} quorum and fault tolerance, such a topology introduces inherent network and CPU overhead due to state replication. Since the primary objective of this controlled experiment is to evaluate the specific resource overhead ($H_{1,3}$) and diagnostic effectiveness ($H_{1,1}$, $H_{1,2}$) of the PANOPTES observability architecture, we adopted a Minimum Distributed Topology consisting of 1 Control Plane (Server/Master) node and 2 Worker (Agent) nodes, each strictly constrained to $2\,\text{vCPUs}$ and $4096\,\text{MiB}$ of RAM.

This 3-node configuration is widely adopted in cloud computing experimental research as it achieves two fundamental goals: (1) via a control-plane \texttt{NoSchedule} taint (\texttt{node-role.kubernetes.io/master=true:NoSchedule}), it strictly isolates Control Plane components from the Data Plane, ensuring that measured worker overhead is exclusively attributed to the application and observability agents; and (2) the presence of multiple worker nodes enforces inter-node network communication, providing a realistic topology to evaluate Distributed Tracing and network telemetry that cannot be faithfully simulated in single-node clusters.

\subsection{Evolution of the Virtualization Substrate (Vagrant $\rightarrow$ Multipass $\rightarrow$ K3d)}
\label{subsec:virtualization-evolution}

In accordance with the iterative \textit{build-and-evaluate} Design Cycle of Design Science Research \cite{hevner_2007, dresch_2015}, the underlying virtualization layer underwent three systematic engineering iterations prior to final data collection, as formally recorded in \textbf{ADR-0006}:

\begin{enumerate}
    \item \textbf{Iteration 1 --- Vagrant with Oracle VirtualBox (Type-2 Hypervisor):} The initial prototype utilized Vagrant to orchestrate three VirtualBox VMs. However, on a Windows~11 host running Hyper-V and Virtualization-Based Security (WSL2/WHPX), VirtualBox is forced into software-emulated execution (\textit{Native Execution Manager / NEM fallback}). This induced severe virtual disk I/O degradation, elevated \texttt{etcd} \texttt{fsync} latencies, and intermittent Flannel VXLAN packet drops across the virtual network interfaces, destabilizing the cluster under steady-state microservice load.

    \item \textbf{Iteration 2 --- Canonical Multipass with Native Hyper-V (Type-1 Hypervisor):} To eliminate Type-2 hypervisor I/O bottlenecks, the testbed was migrated to Canonical Multipass backed directly by the native Windows Hyper-V hypervisor (provisioning scripts documented in Appendix~\ref{app:multipass-commands}). While Multipass resolved the disk I/O bottleneck, an architectural boundary remained: the automated experimental orchestrator (Ansible, Helm, \texttt{kubectl}, and the Python RCA engines) executed inside the WSL2 Linux environment, whereas the Multipass VMs resided on the external Hyper-V virtual switch. Bridging these two environments required Windows TCP port-proxying (\texttt{netsh interface portproxy v4tov4}). Under sustained 30-trial Chaos Mesh campaigns (\texttt{tc-netem} delays and forced pod kills), the cross-hypervisor NAT bridge exhibited intermittent \texttt{kubectl port-forward} resets and Hyper-V dynamic memory ballooning jitter, threatening measurement precision for $MTTDiag$.

    \item \textbf{Iteration 3 (Definitive Substrate) --- K3d with Hard Linux Control Group (\texttt{cgroup}) Quotas on WSL2:} To preserve the exact 3-node distributed topology and hardware quotas ($2\,\text{vCPUs}$ and $4096\,\text{MiB}$ RAM per node) while eliminating cross-VM NAT bridging and hypervisor ballooning jitter, the final experimental campaigns were executed using \textbf{K3d} (containerized multi-node Rancher K3s orchestrated via Docker directly inside the native WSL2 Linux kernel, documented in Appendix~\ref{appendix:c}) \cite{bernstein_2014}. Immediately upon cluster creation (\texttt{1 server + 2 agents}), strict kernel scheduler (\texttt{cpu.max}) and memory (\texttt{memory.max}) limits with zero swap tolerance are enforced on each node via \texttt{docker update --cpus="2.0" --memory="4g" --memory-swap="4g"}. Because the Python RCA engines and the K3d cluster nodes share the same native Linux network stack, all API and telemetry queries traverse local kernel loopback/bridge interfaces with sub-millisecond deterministic latency.
\end{enumerate}

\subsection{Host Environment Specification}
\label{subsec:host-environment}

To ensure transparency, internal validity, and full reproducibility of the controlled experiment, we detail the hardware and software specifications of the physical host machine. Conducting the entire factorial evaluation on a dedicated physical host isolates the testbeds from external wide-area network latencies and multi-tenant cloud interference (the ``noisy neighbor'' effect) \cite{kuria_2024}.

Both the Vanilla baseline and PANOPTES scenarios were provisioned sequentially on a host equipped with an 11th Gen Intel\textsuperscript{\tiny\textregistered} Core\textsuperscript{\tiny\texttrademark} i7-11800H processor (8 Physical Cores, 16 Logical Threads, $2.30\,\text{GHz}$ base frequency) and $64.0\,\text{GB}$ of physical RAM. Storage operations were backed by a $1\,\text{TB}$ NVMe SSD (SK Hynix PC711), delivering sequential read speeds of $3,021\,\text{MB/s}$ and sequential write speeds of $2,461\,\text{MB/s}$. High NVMe IOPS and low \texttt{fsync} latency are methodologically critical to guarantee that neither the Kubernetes \texttt{etcd}/SQLite state store nor the telemetry storage backends (Prometheus TSDB, Loki chunks, and Tempo blocks) experience disk I/O bottlenecks.

The host operating system is Microsoft Windows~11 Home Single Language (Build 26200) running the WSL2 Linux kernel with tuned file-descriptor and \texttt{inotify} limits (\texttt{fs.inotify.max\_user\_instances=8192}, \textbf{ADR-0005}). Across all scenarios, the Kubernetes distribution was deterministically locked to Rancher K3s (v1.34.5+k3s1), a CNCF-certified lightweight distribution whose minimal control-plane footprint ensures that baseline resource consumption ($R_{\text{workload}}$) reflects the monitored microservices rather than orchestrator bloat.
