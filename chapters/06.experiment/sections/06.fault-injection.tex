\section{Fault Injection Implementation}
\label{sec:fault-injection-impl}

Consistent with the Chaos Engineering methodology defined in Chapter~\ref{chap:cloud-computing}, we utilize Chaos Mesh (v2.6.3) to programmatically inject controlled perturbations into our target microservices cluster. The fault campaigns defined in Chapter~\ref{chap:methodology} are synthesized dynamically at runtime as Kubernetes Custom Resource Definitions (CRDs) scoped to the \texttt{otel-demo} namespace.

To prevent collateral perturbation of backing data stores that share prefix labels with stateless microservices (for example, preventing a fault targeting \texttt{cart} from inadvertently hitting the \texttt{valkey-cart} Redis cache), the orchestrator resolves the exact active pod name via the label selector \texttt{app.kubernetes.io/component=<target>} and injects the fault using explicit pod-instance binding (\texttt{spec.selector.pods}), as formalized in \textbf{ADR-0004}. We evaluate three declarative fault injection profiles:

\subsection{Pod-Level Disruption (PodChaos)}
The first campaign simulates an abrupt container runtime crash or Out-Of-Memory (OOM) termination of a target microservice instance, forcing the Kubernetes control plane to execute self-healing and reschedule the pod while interrupting active TCP/gRPC streams. This profile evaluates the preservation of forensic container logs in Loki and connection-reset exception attribution after container destruction. \subsection{Network-Level Performance Degradation (NetworkChaos)}
The second campaign introduces severe service-to-service performance degradation by injecting synthetic Linux kernel \texttt{tc-netem} delay into the target pod's network namespace. In accordance with Chaos Mesh v2.6.3 admission webhook validation rules (\textbf{ADR-0004}), when no secondary \texttt{target} block is specified, the perturbation direction is explicitly set to \texttt{to} (\texttt{direction: to}) with a $2000\,\text{ms}$ latency and $100\,\text{ms}$ jitter. This tests distributed trace self-time decomposition in Grafana Tempo and upper-percentile ($p95$) latency detection in Prometheus under cascading upstream timeouts. \subsection{Resource Saturation (StressChaos)}
The third campaign simulates compute starvation and noisy-neighbor CPU throttling by spawning \texttt{stress-ng} workers inside the target container's control group (\texttt{cgroup}), saturating 2 CPU workers at $100\%$ load for $180\,\text{s}$. This profile assesses how rapidly the diagnostic engines correlate cgroup CPU saturation in Prometheus with degraded span execution or container log anomalies.
