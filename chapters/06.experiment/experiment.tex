\chapter{OBSERVABILITY EXPERIMENT IMPLEMENTATION}
\label{chap:experiment-implementation}

This chapter details the technical implementation of the experimental design defined in the previous chapter. To satisfy the requirement for scientific reproducibility, the entire experimental testbed—from the virtualization layer to the application deployment—was codified using Infrastructure as Code (IaC) principles.

Although cloud-managed Kubernetes services reflect prevalent industry practices, this research opted for a locally hosted, on-premise experimental testbed. This methodological decision is strictly grounded in the necessity for internal validity during the controlled experiment. Public cloud environments are inherently susceptible to multi-tenancy resource contention and the ``noisy neighbor'' effect, which introduce unpredictable fluctuations in CPU, memory, and network latency \cite{kuria_2024}.

Since the evaluation of the PANOPTES architecture requires precise measurement of resource overhead ($H_{1b}$), a controlled local environment eliminates external infrastructural noise, ensuring that metric variations are directly attributable to the observability agents rather than underlying cloud provider anomalies. Furthermore, this approach guarantees full administrative access to both the control and data planes, and promotes research reproducibility without incurring financial costs for future validations.

We describe the instantiation of the PANOPTES reference architecture, the configuration of the baseline environment (Vanilla), and the deployment of the target microservices workload used to generate telemetry data.

\section{Experiment Execution Procedure}
\label{sec:execution-procedure}

To guarantee statistical reliability and mitigate learning bias, the experimental execution follows a strict, repeatable protocol for all 30 iterations ($N=30$) defined in the methodology. The execution procedure is divided into four chronological phases:

\begin{enumerate}
    \item \textbf{Environment Reset:} Before each iteration, the Kubernetes namespace containing the Online Boutique is entirely deleted and recreated using the Ansible playbooks. This ensures that no residual state (e.g., OOMKilled pods, cached memory) influences the subsequent test.
    \item \textbf{Load Generation:} The \textit{Loadgenerator} microservice is initiated to simulate concurrent user traffic. The system is allowed a 5-minute warm-up period to stabilize CPU and memory baselines.
    \item \textbf{Fault Injection ($T_0$):} The Chaos Mesh CRD (e.g., \texttt{PodChaos} or \texttt{NetworkChaos}) is applied to the cluster via the Kubernetes API. The exact timestamp of the API server acknowledgment is recorded as $T_0$.
    \item \textbf{Diagnosis and MTTD Measurement ($T_1$):} The operator attempts to identify the root cause of the anomaly. The protocol differs strictly between the two groups:
    \begin{itemize}
        \item \textbf{Vanilla Kubernetes (Control):} The operator is restricted to native CLI commands (e.g., \texttt{kubectl get events}, \texttt{kubectl describe}, \texttt{kubectl logs}). The timestamp $T_1$ is recorded when the operator successfully outputs the exact error log of the failing microservice.
        \item \textbf{PANOPTES (Experimental):} The operator utilizes the Grafana UI. $T_1$ is recorded the moment the operator visually correlates the latency/error metric to the specific failing \texttt{traceID} and its corresponding log line.
    \end{itemize}
\end{enumerate}

The Mean Time to Detect (MTTD) for each iteration is calculated as the delta between $T_1$ and $T_0$ ($\Delta T = T_1 - T_0$). If the root cause is not identified within 5 minutes (300 seconds), the iteration is marked as a diagnostic failure, consistent with the predefined evaluation criteria.

\section{Preliminary Validation}
\label{sec:preliminary-validation}

While the complete execution of the 30 experimental iterations and their subsequent statistical analysis are reserved for future work, the PANOPTES testbed has been successfully instantiated and validated. Preliminary executions confirm that the infrastructure components interact as mathematically specified in the architectural design.

\begin{figure}[htbp]
  \centering
  \includegraphics[width=0.9\textwidth]{images/experiment/grafana_preliminary.png}
  \caption{Grafana interface successfully displaying correlated metrics and traces from the experimental workload.}
  \label{fig:grafana_preliminary}
\end{figure}

Figure \ref{fig:grafana_preliminary} demonstrates the "Single Pane of Glass" operational state, proving that the OpenTelemetry collectors are actively scraping the target microservices and successfully forwarding the telemetry data to the Prometheus, Loki, and Tempo backends. Furthermore, the Chaos Mesh operator has been tested and confirmed to successfully disrupt the network namespaces of the target pods without crashing the underlying K3s control plane, validating the safety of the fault injection mechanism.
