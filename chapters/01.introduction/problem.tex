\section{PROBLEM STATEMENT}
\label{sec:problem}

While several tools emerged to address different pillars of observability, such as in microservices \cite{faseeha_2025}, the Kubernetes (K8S) architecture and default installation \cite{johansson_2022} do not include such tools. In fact, there is a long list of ways to install a K8S cluster \cite{luksa_2018}. Therefore, to address this predicament, it is necessary to use an automated, secure tool to install observability tools, such as Helm Charts.

Considering this scenario, this study aims to investigate how to tackle this complexity using open-source tools to monitor and observe cloud-native applications. This research delves into one central question and four secondary research questions surrounding observability architecture, as detailed in Section~\ref{subsec:research-questions}.

\subsection{Research Questions}
\label{subsec:research-questions}

\textbf{Main Research Question (MRQ):} \textit{How can a reference architecture for observability in Kubernetes, based on open standards, enhance the ability to diagnose faults in microservices compared to the platform's native monitoring mechanisms?}

To provide a comprehensive answer to this overarching question, four Secondary Research Questions (SRQs) have been delineated:

\textbf{SRQ1:} \textit{What are the minimum architectural requirements and open-source components needed to compose a complete observability layer (Metrics, Logs, and Tracing) in Kubernetes orchestrators?}

\textbf{SRQ2:} \textit{How can we instantiate a reference architecture using open-source tools that ensures semantic integration between the pillars of observability without excessively burdening cluster resources?}

\textbf{SRQ3:} \textit{What is the impact of the proposed architecture on the effectiveness of fault detection and root-cause diagnosis compared to a standard (Vanilla Baseline) Kubernetes installation?}

\textbf{SRQ4:} \textit{How can the evolutionary stages of observability in cloud-native environments be classified, and what are the primary gaps in current open-source implementations?}

\subsection{Research Objectives}

To answer the research questions, the main objective of this thesis is to \textbf{propose, instantiate, and empirically validate} an observability reference architecture for cloud-native applications on Kubernetes.

Specifically, the Specific Objectives (SOs) are:

\textbf{SO1:} \textit{To \textbf{identify and define} the essential architectural requirements and components necessary to establish a cohesive observability layer.}

\textbf{SO2:} \textit{To \textbf{design and implement} an open-source reference architecture instance that integrates metrics, logs, and traces within a bounded operational resource envelope.}

\textbf{SO3:} \textit{To \textbf{evaluate} the proposed architecture's effectiveness in diagnosing faults through controlled Chaos Engineering experiments, comparing its diagnostic latency ($MTTDiag$) and accuracy ($Acc$) against a Kubernetes baseline.}

\textbf{SO4:} \textit{To \textbf{conduct} a Rapid Review of the state-of-the-art to identify current architectural gaps and propose an Observability Maturity Model (OMM) that categorizes the evolutionary stages of telemetry management.}
