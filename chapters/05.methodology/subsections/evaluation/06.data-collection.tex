\subsection{Instrumentation and Data Collection}
\label{sec:data-collection}

The data collection and experimental instrumentation pipelines are fully codified and automated to ensure scientific reproducibility, eliminate operator variance, and mitigate observer-induced interference across all $N = 30$ iterations:

\begin{itemize}
    \item \textbf{Resource Overhead Profiling (Testing $H_{1,3}$):} To measure the static cost of observability without triggering the observer effect in the control baseline, resource metrics are captured via differential mechanisms:
    \begin{itemize}
        \item \textit{Scenario 1 (Vanilla Baseline):} CPU and memory consumption are queried out-of-band via the native Kubernetes Metrics Server API at regular $5\,\text{s}$ intervals. This ensures zero telemetry forwarder overhead within the monitored microservices namespaces.
        \item \textit{Scenario 2 (PANOPTES):} Resource utilization across the \texttt{monitoring} namespace (hosting the OpenTelemetry Collector, Prometheus, Loki, Promtail, and Tempo pods) is captured continuously via the \texttt{container\_cpu\_usage\_seconds\_total} and \texttt{container\_memory\_rss} metrics exposed by cAdvisor and scraped by Prometheus. The resulting time-series vectors are exported to CSV format for subsequent bounded overhead evaluation against $\theta = 0.15 \cdot \sum R_{\text{workload}}$.
    \end{itemize}

    \item \textbf{Fault Injection Instrumentation (Testing $H_{1,1}$ and $H_{1,2}$):} Controlled perturbations are orchestrated programmatically via Chaos Mesh Custom Resource Definitions (CRDs) across three distinct fault campaigns designed to evaluate the multi-modal integration of the observability stack:
    \begin{itemize}
        \item \textit{Network-Level Latency (NetworkChaos):} Targets the network namespace of a microservice (e.g., \texttt{payment}) with an induced latency of $250\,\text{ms}$ ($\pm 50\,\text{ms}$ jitter, correlation of $25\%$, in \texttt{direction: to}), designed to assess the performance degradation propagation and evaluate the \textbf{Distributed Tracing (Tempo)} correlation.
        \item \textit{Pod-Level Disruption (PodChaos):} Triggers a forced pod termination (\texttt{pod-kill}) on ephemeral services (e.g., \texttt{frontend} or \texttt{cart}) to evaluate how the architecture preserves forensic evidence across abrupt container lifecycles, validating the \textbf{Log Aggregation (Loki)} collection and trace termination boundaries.
        \item \textit{Resource Saturation (StressChaos):} Dynamically injects synthetic CPU load ($100\%$ CPU cores utilization) or virtual memory leaks to trigger resource bounds and Out-Of-Memory (OOM) events, validating the sensitivity of the \textbf{Metric Collection (Prometheus)} alert rules and threshold violations.
    \end{itemize}
    The injection process synchronizes the cluster state, enforces a $30\,\text{s}$ pre-injection stabilization window, and extracts the authoritative API Server acknowledgment timestamp ($T_0$) directly from the Custom Resource metadata in Unix epoch format.

    \item \textbf{Diagnostic Traceability and Latency Logging:} Diagnostic workflows across Scenarios 3 and 4 are instrumented with strict timestamp capture:
    \begin{itemize}
        \item In Scenario 3 (Vanilla), the investigator's CLI execution sequence is logged, capturing the precise timestamp ($T_{\text{diag}}$) when the root-cause service is successfully identified from unstructured container logs or descriptions.
        \item In Scenario 4 (PANOPTES), the Grafana correlation workflow captures the timestamp ($T_{\text{diag}}$) upon rendering the correlated Tempo trace and contextual Loki error log originating from the Prometheus latency threshold violation.
        \item All diagnostic records are appended to an experiment audit file (\texttt{experiment-results.csv}), documenting iteration id, $T_0$, $T_{\text{diag}}$, computed $MTTDiag = T_{\text{diag}} - T_0$, and binary accuracy outcome ($Acc \in \{0, 1\}$).
    \end{itemize}

    \item \textbf{Target Workload and Load Generation:} The evaluated workload is instantiated using the polyglot OpenTelemetry Astronomy Shop demo. Steady-state traffic is generated by the application's native, continuous \texttt{loadgenerator} service, which simulates concurrent synthetic user sessions (browsing products, shopping cart operations, and checkout sequences). Operating under a predictable, deterministic synthetic load profile ensures that the microservices transactions are actively traversing the inter-service network when latency anomalies are introduced.
\end{itemize}
