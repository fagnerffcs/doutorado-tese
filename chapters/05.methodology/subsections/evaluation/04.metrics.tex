\textbf{Analytical and Statistical Protocol}

The empirical datasets gathered across all experimental scenarios ($N = 30$ runs per scenario) are evaluated under the following inferential criteria:
\begin{itemize}
    \item \textbf{Diagnostic Accuracy ($Acc$, Testing $H_{1,2}$):} Evaluated as a binary categorical variable ($1 = \text{Success}, 0 = \text{Failure}$) based on whether the automated diagnostic engine correctly isolates the ground-truth perturbed microservice locus within the maximum operational window ($T_{\text{max}} = 300\,\text{s}$) \cite{wang_2024}. Differences in diagnostic success rates between the Vanilla baseline (Scenario 3) and PANOPTES (Scenario 4) are evaluated using \textit{Fisher's Exact Test} ($2\times2$ contingency table), ensuring exact conditional probabilities without relying on asymptotic $\chi^2$ approximations \cite{agresti_2007}.
    
    \item \textbf{Diagnostic Efficiency ($MTTDiag$, Testing $H_{1,1}$):} Diagnostic duration represents continuous ratio data. Distribution normality is formally assessed via the \textit{Shapiro-Wilk test} ($\alpha = 0.05$). When normality is violated---a structural property of latency and algorithmic convergence durations in distributed systems \cite{barata_2026}---we employ the non-parametric \textit{Mann-Whitney U Test} (two-tailed, $\alpha = 0.05$) to evaluate whether the rank-sum distribution of $MTTDiag_{\text{PANOPTES}}$ is stochastically smaller than $MTTDiag_{\text{Vanilla}}$ \cite{wohlin_2012}.
    
    \item \textbf{Bounded Overhead Compliance ($\Delta_{CPU}, \Delta_{RAM}$, Testing $H_{1,3}$):} To test whether the static cost of observability violates the operational tolerance envelope ($\theta = 0.15 \cdot \sum R_{\text{workload}}$), the net overhead of the PANOPTES stack ($R_{\text{PANOPTES}} = R_{\text{S2}} - R_{\text{S1}}$) is evaluated using a one-tailed, one-sample hypothesis test (\textit{One-Sample Wilcoxon Signed-Rank Test} if non-normal, or \textit{One-Sample $t$-test} if normal) against the constant boundary $\theta$.
\end{itemize}

\textbf{Diagnostic Latency Operationalization (MTTDiag vs. MTTD)}

A critical methodological requirement in evaluating diagnostic efficiency is strictly separating initial anomaly detection ($T_{\text{detect}}$) from verified root-cause diagnosis ($T_{\text{diag}}$) \cite{wang_2024}. In complex cloud-native architectures, an initial ingress degradation or HTTP timeout signals an outward disturbance, whereas isolating the true failing component (e.g., distinguishing a downstream network delay from upstream cascade timeouts) requires multi-signal inspection across microservices \cite{barata_2026}.

The Mean Time to Diagnose ($MTTDiag$) for each iteration is computed as:
\begin{equation}
    MTTDiag = T_{\text{diag}} - T_0
\end{equation}
where $T_0$ is the authoritative epoch timestamp of the Chaos Mesh injection acknowledgment returned by the Kubernetes API Server, and $T_{\text{diag}}$ is the exact moment the automated diagnostic engine outputs its localized culprit. If an iteration reaches $T_{\text{max}} = 300\,\text{s}$ without programmatic convergence to the root cause, it is registered as an investigative failure ($Acc = 0$) and its duration is right-censored at $300\,\text{s}$ for survival and non-parametric evaluations.

\textbf{Comparative Automated Diagnostic Workflows}

To ensure unbiased, deterministic, and reproducible measurement of $T_{\text{diag}}$ across Scenarios 3 and 4, the evaluation replaces subjective human operators with an algorithmic Root Cause Analysis (RCA) agent \cite{wang_2024, barata_2026}. The agent acts under two strictly isolated operational workflows:

\begin{enumerate}
    \item \textbf{Vanilla Diagnostic Workflow (Scenario 3):} The agent is restricted to standard Kubernetes cluster API endpoints (emulating a systematic CLI-based SRE inspection). Starting from the edge ingress (\texttt{frontend}), the engine executes an unindexed breadth-first search (BFS) across active application pods. For each candidate microservice, it executes remote Kubernetes API calls to fetch recent container log buffers, parses them for exception signatures (e.g., timeout deadlines, RPC handshakes, or HTTP 5xx codes), and polls the native \texttt{metrics-server} API. The diagnostic timestamp ($T_{\text{diag}}$) is recorded when the engine matches the degraded downstream signature. This duration intrinsically captures the compounding operational friction of remote API round-trips, network I/O serialization, and brute-force text log filtering \cite{wang_2024}.
    
    \item \textbf{PANOPTES Diagnostic Workflow (Scenario 4):} The agent directly queries the unified observability interfaces (Prometheus and Tempo APIs) provided by the PANOPTES reference architecture. When an ingress degradation is observed, the engine queries Tempo for traces exhibiting latencies in the p95/p99 tail. It performs a directed traversal over the structured call graph (\texttt{parent\_pod} $\rightarrow$ \texttt{child\_pod}) to pinpoint the exact span exhibiting maximal duration inflation or anomalous error status \cite{wang_2024, barata_2026}. The diagnostic timestamp ($T_{\text{diag}}$) is registered when the anomalous span locus is isolated.
\end{enumerate}

\textbf{Automated Telemetry Capture and Lifecycle}

To eliminate observer-induced interference and ensure complete reproducibility across all $N = 30$ iterations:
\begin{itemize}
    \item \textbf{Timestamp Persistence:} The test orchestration suite automates injection via Chaos Mesh, recording $T_0$ directly from the API Server state machine and logging $T_{\text{diag}}$ upon algorithmic completion into a standardized CSV record (\texttt{experiment-results.csv}).
    \item \textbf{Resource Profiling:} Cluster-wide CPU and RSS memory consumption are captured at regular $5\,\text{s}$ intervals using the Kubernetes Metrics Server in Scenario 1 and the cAdvisor/Prometheus exporter pipeline in Scenario 2, ensuring stable steady-state quantification for overhead modeling.
    \item \textbf{Post-Processing and Reproducibility:} At the conclusion of the $N = 30$ iterations per scenario, the recorded datasets are processed using an offline Python analysis pipeline (backed by \textit{SciPy} and \textit{Pandas}). This pipeline evaluates normality via the Shapiro-Wilk test, executes the Mann-Whitney U rank-sum evaluations, computes Fisher's Exact contingency tables, and verifies the one-sample bounded overhead inequalities presented in Chapter~\ref{chap:experiment-implementation}.
\end{itemize}
