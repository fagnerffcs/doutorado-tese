\textbf{Analytical and Statistical Protocol}

The empirical datasets gathered across the experimental campaigns are evaluated under the following inferential criteria:
\begin{itemize}
    \item \textbf{Diagnostic Accuracy ($Acc$, Testing $H_{1,2}$):} Evaluated as a binary categorical variable ($1 = \text{Success}, 0 = \text{Failure}$) based on whether the automated diagnostic engine correctly isolates the ground-truth perturbed microservice locus within the maximum operational window ($T_{\text{max}} = 300\,\text{s}$) \cite{wang_2024}. Overall differences in diagnostic success rates between Scenario~3 and Scenario~4 (4a/4b) are evaluated using \textit{Fisher's Exact Test} ($2\times2$ contingency table) \cite{agresti_2007}, complemented by \textit{McNemar's Test} to exploit the trial-by-trial pairing established in \textbf{ADR-0001} and stratified accuracy breakdowns across the three fault classes (\texttt{network-delay}, \texttt{pod-kill}, and \texttt{cpu-stress}).
    
    \item \textbf{Diagnostic Efficiency ($MTTDiag$, Testing $H_{1,1}$):} Diagnostic duration represents continuous ratio data subject to right-censoring at $300\,\text{s}$. Distribution normality is formally assessed via the \textit{Shapiro-Wilk test} ($\alpha = 0.05$). When normality is violated---a structural property of latency and algorithmic convergence durations in distributed systems \cite{barata_2026}---we employ both the non-parametric \textit{Mann-Whitney U Test} (for independent group comparison) and the paired \textit{Wilcoxon Signed-Rank Test} (leveraging the exact trial-by-trial pairing of \textbf{ADR-0001}) to evaluate whether $MTTDiag_{\text{PANOPTES}}$ is stochastically smaller than $MTTDiag_{\text{Vanilla}}$ \cite{wohlin_2012}.
    
    \item \textbf{Bounded Overhead Compliance ($\Delta_{\text{CPU}}, \Delta_{\text{RAM}}$, Testing $H_{1,3}$):} To test whether the steady-state cost of observability respects the operational tolerance envelope ($\theta = 0.15 \cdot \sum R_{\text{workload}}$), the net overhead of the PANOPTES stack ($R_{\text{PANOPTES}}$ across $N=60$ independent samples) is evaluated using a one-tailed hypothesis test (\textit{One-Sample Wilcoxon Signed-Rank Test} if non-normal, or \textit{One-Sample $t$-test} if normal) against the constant threshold $\theta$.
\end{itemize}

\textbf{Diagnostic Latency Operationalization ($MTTDiag$ vs. $MTTD$)}

A critical methodological requirement in evaluating diagnostic efficiency is strictly separating initial anomaly detection ($T_{\text{detect}}$) from verified root-cause diagnosis ($T_{\text{diag}}$) \cite{wang_2024}. In complex cloud-native architectures, an initial ingress degradation or HTTP timeout merely signals an outward disturbance, whereas isolating the true failing downstream component (e.g., distinguishing a downstream network delay in \texttt{payment} from upstream cascade timeouts in \texttt{checkout} or \texttt{frontend}) requires causal decomposition across microservices \cite{barata_2026}.

The Mean Time to Diagnose ($MTTDiag$) for each iteration is computed as:
\begin{equation}
    MTTDiag = T_{\text{diag}} - T_0
\end{equation}
where $T_0$ is the authoritative UTC timestamp captured immediately upon Chaos Mesh CRD creation by the Kubernetes API Server, and $T_{\text{diag}}$ is the exact moment the automated diagnostic engine converges on a candidate culprit. If an iteration reaches $T_{\text{max}} = 300\,\text{s}$ without programmatic convergence, it is registered as an investigative timeout ($Acc = 0$, $\text{censored} = \text{True}$) and right-censored at $300\,\text{s}$. If the engine converges prematurely on an incorrect microservice, the actual elapsed time is preserved with $Acc = 0$ and $\text{censored} = \text{False}$.

\textbf{Comparative Automated Diagnostic Workflows}

To ensure unbiased, deterministic, and reproducible measurement of $T_{\text{diag}}$ across Scenarios~3, 4a, and~4b, the evaluation replaces human operators with deterministic Root Cause Analysis (RCA) agents \cite{wang_2024, barata_2026} operating under identical polling cadences ($3\,\text{s}$ initial propagation wait followed by $4\,\text{s}$ polling cycles, \textbf{ADR-0001}):

\begin{enumerate}
    \item \textbf{Vanilla CLI Diagnostic Workflow (Scenario 3):} The agent is restricted exclusively to native Kubernetes CLI endpoints (\texttt{kubectl get pods}, \texttt{kubectl logs --since-time=}$T_0$, and \texttt{kubectl top pods}). In each polling cycle, it inspects pod lifecycle states and restart deltas against a pre-injection baseline, executes breadth-first container log scraping for exception and timeout signatures, and polls CPU millicore saturation via \texttt{metrics-server}. This duration intrinsically captures the operational friction of sequential CLI round-trips, unindexed log scanning, and $15\,\text{s}$ metric-scraper lag \cite{wang_2024}.
    
    \item \textbf{Monomodal Trace Diagnostic Workflow (Scenario 4a):} The agent queries Grafana Tempo HTTP endpoints for traces generated within $[T_0 - 2\,\text{s}, T_{\text{now}}]$ and attributes the root cause to spans exhibiting error status codes or the longest total duration. This baseline tests the limits of single-pillar tracing when confronted with non-HTTP resource saturation (\texttt{cpu-stress}) or abrupt container termination (\texttt{pod-kill}) alongside cascading parent spans.

    \item \textbf{PANOPTES Multimodal Correlated Workflow (Scenario 4b):} Operationalizing Control Principles \texttt{CP1} and \texttt{CP2}, the agent queries Prometheus, Loki, and Tempo strictly via HTTP APIs without any \texttt{kubectl} fallback (\textbf{ADR-0002}). It combines PromQL queries (restart deltas, cgroup CPU saturation rates, and $p95$ span duration), LogQL exception stream aggregation, and OTLP trace analysis using \textit{exclusive span self-time decomposition} ($T_{\text{self}} = T_{\text{span}} - \sum T_{\text{children}}$) and L4/L7 peer attribution (\texttt{server.address}, \texttt{net.peer.name}) to isolate the true downstream culprit \cite{barata_2026}.
\end{enumerate}

\textbf{Automated Telemetry Capture and Lifecycle}

To eliminate observer-induced interference and ensure complete reproducibility:
\begin{itemize}
    \item \textbf{Timestamp Persistence:} The orchestration suite automates fault injection via Chaos Mesh, recording $T_0$ and $T_{\text{diag}}$ directly into standardized CSV audit logs along with the injected fault class and censoring flag.
    \item \textbf{Anti-Pseudoreplication Resource Profiling (ADR-0003):} Cluster-wide node and pod CPU/RAM metrics are captured at $16\,\text{s}$ intervals across $N=60$ samples ($960\,\text{s}$) in Scenarios~1 and~2, preventing duplicate reads from the $15\,\text{s}$ K3s \texttt{metrics-server} cache window.
    \item \textbf{Post-Processing and Reproducibility:} Recorded datasets are processed via a reproducible Python statistical pipeline (\textit{SciPy} and \textit{Pandas}) that executes Shapiro-Wilk normality tests, Mann-Whitney U and paired Wilcoxon Signed-Rank tests, Fisher's Exact and McNemar's contingency tests, and one-sample bounded overhead evaluations.
\end{itemize}
