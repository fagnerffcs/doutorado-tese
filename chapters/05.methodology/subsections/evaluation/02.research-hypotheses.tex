\subsection{Research Hypotheses}

To rigorously evaluate the utility, diagnostic efficiency, and operational feasibility of the PANOPTES reference architecture, we formulate three formal research hypotheses. These hypotheses are grounded in the theoretical dualism between system observability and controllability, directly addressing Secondary Research Questions \textbf{SRQ2} and \textbf{SRQ3}.

Rather than evaluating trivial failure detection at the orchestrator level (e.g., node or pod crashes natively reported by the Kubernetes API Server), our evaluation targets non-trivial, latent distributed anomalies where root-cause isolation requires semantic correlation across multiple telemetry modalities (metrics, traces, and logs).

\textbf{Hypothesis 1: Diagnostic Efficiency (Mean Time to Diagnose --- $MTTDiag$)}\\
We postulate that the semantic correlation across distributed traces, contextual logs, and golden signal metrics instantiated in PANOPTES significantly reduces the latency required to isolate the true root cause of distributed anomalies compared to standard Kubernetes CLI-based inspection.
\begin{itemize}
    \item $H_{0,1}$ (Null Hypothesis): There is no statistically significant reduction in the Mean Time to Diagnose ($MTTDiag$) between standard Kubernetes CLI-based diagnostic workflows and the PANOPTES architecture during latent failure scenarios ($MTTDiag_{\text{PANOPTES}} \ge MTTDiag_{\text{Vanilla}}$).
    \item $H_{1,1}$ (Alternative Hypothesis): The PANOPTES reference architecture yields a statistically significant reduction in the Mean Time to Diagnose ($MTTDiag$) compared to standard Kubernetes CLI-based diagnostic workflows ($MTTDiag_{\text{PANOPTES}} < MTTDiag_{\text{Vanilla}}$).
\end{itemize}

\textbf{Hypothesis 2: Diagnostic Accuracy in Latent Faults ($Acc$)}\\
In distributed microservice topologies, partial degradations (such as injected network delays, CPU throttling, or cascading upstream timeouts) frequently manifest without orchestrator-level failure events or require distinguishing the originating downstream bottleneck from upstream caller spans. We postulate that unified multi-pillar observability provides complete causal context, yielding a significantly higher probability of correct root-cause identification within a defined operational time window ($T_{\text{max}} = 300\,\text{s}$).
\begin{itemize}
    \item $H_{0,2}$ (Null Hypothesis): The proportion of successful root-cause diagnoses ($p_1$) achieved using the PANOPTES architecture is equal to or less than the proportion ($p_0$) achieved through native Kubernetes inspection or monomodal baseline tools ($p_1 \le p_0$).
    \item $H_{1,2}$ (Alternative Hypothesis): The proportion of successful root-cause diagnoses achieved using the PANOPTES architecture is strictly higher than that achieved through native Kubernetes inspection or monomodal baseline tools ($p_1 > p_0$).
\end{itemize}

\textbf{Hypothesis 3: Bounded Resource Overhead (Operational Envelope)}\\
Deploying telemetry forwarders, collectors, and storage backends inevitably introduces computational and memory overhead over a raw Kubernetes installation. Therefore, testing for a mere non-zero difference in resource consumption ($\text{Vanilla} < \text{PANOPTES}$) is academically trivial and provides no scientific insight.

Instead, grounded in the capacity planning guidelines of the \textit{Google SRE Book} \cite{beyer_2016} and Kubernetes resource management primitives \cite{bernstein_2014}, we evaluate a \textit{Bounded Overhead Hypothesis}. Architecturally, an in-cluster observability stack exhibits two distinct resource profiles: (i)~\textbf{dynamic compute overhead (CPU)}, which scales proportionally with workload telemetry throughput ($O(\text{spans, metrics, logs/s})$) and must remain confined within a strict fraction ($\theta_{\text{CPU}} = 15\%$) of the monitored workload's CPU consumption; and (ii)~\textbf{resident memory footprint (RAM)}, where centralized time-series and trace storage backends (Prometheus TSDB head blocks, Loki chunk buffers, and Tempo ingesters) maintain a fixed baseline working-set allocation in addition to lightweight node-level collection agents, which must remain within the cluster's provisioned memory capacity envelope ($\theta_{\text{RAM}} \le 30\%$ of total cluster RAM capacity, or $\le 15\%$ at the node-agent collection tier) without inducing kernel swap thrashing or \texttt{OOMKilled} evictions.
\begin{itemize}
    \item $H_{0,3}$ (Null Hypothesis): The steady-state dynamic CPU footprint introduced by the PANOPTES telemetry stack exceeds the proportional tolerance threshold of $\theta_{\text{CPU}} = 15\%$ of the monitored workload ($R_{\text{PANOPTES}}^{\text{CPU}} > 0.15 \cdot R_{\text{workload}}^{\text{CPU}}$), or its resident memory footprint violates the safe cluster capacity envelope ($R_{\text{PANOPTES}}^{\text{RAM}} > \theta_{\text{RAM}}$).
    \item $H_{1,3}$ (Alternative Hypothesis): The steady-state dynamic CPU footprint of the PANOPTES stack remains strictly contained within the proportional operational threshold ($R_{\text{PANOPTES}}^{\text{CPU}} \le 0.15 \cdot R_{\text{workload}}^{\text{CPU}}$) while its resident memory footprint remains bounded within the non-intrusive cluster capacity envelope ($R_{\text{PANOPTES}}^{\text{RAM}} \le \theta_{\text{RAM}}$), preventing \textit{noisy neighbor} contention in resource-constrained environments.
\end{itemize}

\textit{Operational Acceptance Criterion:} While $H_{1,1}$ and $H_{1,2}$ establish statistical superiority in fault isolation, $H_{1,3}$ evaluates runtime non-interference (\texttt{ConH3}). Guided by SRE management overhead principles \cite{beyer_2016}, separating proportional compute overhead ($\Delta_{\text{CPU}}$) from fixed storage-backend memory allocation ($\Delta_{\text{RAM}}$) enables a rigorous evaluation of both collection efficiency and in-cluster storage sizing trade-offs during comparative experimental evaluations.
